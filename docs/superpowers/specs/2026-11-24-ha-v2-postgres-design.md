# HA v2: два вузли, PostgreSQL і Redis із автоматичним перемиканням

Статус: ЗАТВЕРДЖЕНО користувачем 2026-11-24 (синхронна реплікація без strict). Продовжує `2026-11-23-ha-failover-design.md` (v1: оренда в Redis, спільний SQLite на одному вузлі).

## Навіщо
v1 переживає падіння процесу й контейнера, але не втрату вузла: файл SQLite лежить на одному томі, Redis один. Потрібно, щоб
система тривог працювала, коли помирає ціла машина. Розгортання: **два VPS у docker compose плюс третя крихітна машина-свідок**,
усе своє (не керовані сервіси). Користувач вимагає security-first і fail-closed.

## Цілі
1. Втрата будь-якої однієї з трьох машин не зупиняє систему довше за кілька десятків секунд, без втручання людини.
2. Жодного split-brain: у кожен момент писати інциденти й дії може лише одна копія рушія, а БД має лише один master.
3. PostgreSQL замість файлу SQLite для режиму HA: інциденти, рішення операторів, replay, журнал дій із ланцюжком хешів.
4. Redis HA (Sentinel) для сесій, ліміту входів і релея подій.
5. Міграція існуючого файлу `incidents.db` у PostgreSQL одним інструментом, із перевіркою ланцюжка хешів після переносу.
6. Репетиція: профіль compose, що піднімає всі три ролі на одній машині, і скрипт, який вбиває вузли й міряє час перемикання.

## Не цілі
- HA для MQTT-брокера й датчиків (див. відкрите питання 1).
- Резервні копії PostgreSQL (репліка не є копією): лише згадка й рекомендація в README.
- Kubernetes, кілька регіонів, більше двох вузлів даних.
- Зміна типового режиму: SQLite без HA лишається як є, нічого не ламається.

## Антицілі (провал, навіть якщо «працює»)
- Тихий відкат на SQLite чи на пам'ять, коли PostgreSQL налаштовано, але недоступний.
- Два лідери, що пишуть одночасно (навіть на мить).
- Секрети в URL, логах, повідомленнях помилок; незашифровані зв'язки між VPS.
- Послаблення журналу дій: рядки правляться/видаляються, хвіст відрізається непомітно.

## Обмеження
- Автоматичне перемикання без split-brain потребує кворуму з трьох, тому третя машина обов'язкова. Вона не тримає даних.
- Уже діють: fail-closed TLS (`rediss://`, `check_redis_url` дозволяє `redis://` лише на localhost), ACL брокера, ролі, scrypt.
- Існуючі інваріанти HA: лідер сам відраховує термін оренди монотонним годинником від початку запиту поновлення; DEGRADED
  показує тривоги й не змінює нічого; резерв працює на `:memory:` і нічого не пише.

## Підходи (обрано A)
**A (обрано користувачем):** Patroni + etcd для PostgreSQL, Redis Sentinel; etcd і Sentinel по одному на кожній з трьох машин;
оренда лідера переїжджає з Redis у PostgreSQL. **B:** два VPS без свідка, ручний промоут: відхилено, сервіс стоїть, поки людина
не втрутиться. **C:** примусовий лідер без кворуму: відхилено, ризик split-brain суперечить fail-closed.

Підходи до коду сховища (мій вибір, не погоджений користувачем):
- **Тонкий адаптер над DB-API** з двома бекендами (SQLite, PostgreSQL) і невеликим набором діалектних відмінностей (обрано).
  Дає мінімум змін у запитах, без нової важкої залежності.
- SQLAlchemy Core: відхилено, тягне велику залежність і переписування всіх запитів.
- Лише PostgreSQL для HA, а SQLite-код без змін поряд: відхилено, дублює логіку інцидентів і журналу.

## Архітектура

```
 VPS-A                    VPS-B                    witness (без даних)
 ha-a                     ha-b
 Patroni+PG  <--stream--> Patroni+PG
 Redis       <--repl----> Redis
 etcd        <----------> etcd        <---------> etcd
 Sentinel    <----------> Sentinel    <---------> Sentinel
```
- Patroni тримає лідерство PostgreSQL в etcd (кворум 2 з 3). Sentinel вирішує master Redis (кворум 2 з 3).
- Оренда лідера рушія береться з PostgreSQL, а не з Redis. Redis виходить зі шляху запису тривог: його падіння більше не
  переводить рушій у DEGRADED, лише вимикає сесії дашборда (вже fail-closed 503) і релей подій.

### Адаптер сховища
Модуль `service/store.py`: інтерфейс `Db` (execute, executemany, commit, rollback, одна транзакція на виклик), бекенди `SqliteDb`,
`PostgresDb`. Діалектні відмінності, які він ховає:
| SQLite | PostgreSQL |
|---|---|
| `?` | `%s` |
| `INTEGER PRIMARY KEY AUTOINCREMENT`, `lastrowid` | `BIGINT GENERATED ALWAYS AS IDENTITY`, `INSERT ... RETURNING id` |
| `REAL` ts | `DOUBLE PRECISION` |
| `PRAGMA table_info` + `ALTER` | `information_schema` або `ADD COLUMN IF NOT EXISTS` |
| `BEGIN IMMEDIATE` | `SELECT ... FOR UPDATE` |
| `ON CONFLICT(id) DO UPDATE` | те саме (однаково працює) |
| тригери `RAISE(ABORT)` | функція-тригер `RAISE EXCEPTION` |
| `BLOB` replay | `BYTEA` |
Драйвер: `psycopg[binary]` 3.x з пулом, опціональна залежність `dronewatch[postgres]`. Без неї режим postgres не стартує (fail-closed).

### Конфіг
```yaml
storage:
  backend: sqlite            # типово; postgres лише з ha.enabled
  dsn: null                  # postgresql://app@a:5432,b:5432/dw?sslmode=verify-full&target_session_attrs=read-write
                             # пароль через DRONEWATCH_PG_PASSWORD, не в файлі
  connect_timeout_s: 2
  statement_timeout_s: 3
ha:
  lease_store: postgres      # або redis (v1, лише з sqlite)
redis:                       # замінює dashboard.redis_url/ha.redis_url у режимі Sentinel
  sentinels: ["a:26379", "b:26379", "w:26379"]
  master_name: dw
```
Мультихост-DSN з `target_session_attrs=read-write` сам знаходить поточний master після перемикання Patroni: HAProxy не потрібен.
Валідація при старті: `sslmode` має бути `verify-full`; `redis://` без TLS у Sentinel-режимі заборонено (як зараз для не-localhost).

### Оренда й запобіжник у PostgreSQL
Таблиця `ha_lease(id=1, owner, epoch, expires_at)` і `ha_epoch(id=1, epoch)` у тій самій БД, що й дані.
- `acquire`: транзакція, `SELECT ... FOR UPDATE`; якщо оренди нема або `expires_at < now()` (годинник PostgreSQL, не VPS),
  то `epoch = max(lease.epoch, ha_epoch.epoch) + 1`, записується власник і новий термін. Інакше `None`.
- `renew`, `release`, `raise_epoch`: за тим самим протоколом `LeaseStore`, тож `Elector` не змінюється.
- Лідер, як і раніше, відраховує свій термін за монотонним годинником від початку запиту. Годинник БД потрібен лише щоб
  інші не перехопили оренду раніше.
- Запобіжник стає **атомарним із записом**: кожна транзакція запису інциденту, рішення оператора чи запису журналу починається з
  `SELECT epoch FROM ha_epoch FOR SHARE` і порівнює зі своїм epoch до будь-якого запису. Вікна між перевіркою й записом (TOCTOU у
  поточному `fence()`) більше нема. Старий лідер після перемикання отримує `FencedError` і стає резервом.
- Дані й epoch завжди перемикаються разом (одна БД), тому відкат epoch після асинхронної втрати репліки неможливий без втрати
  й самих даних того ж моменту: узгодженість зберігається.

### Журнал дій у PostgreSQL
Таблиця `audit_head(id=1, last_id, head_hash)` оновлюється в тій самій транзакції під `FOR UPDATE`: це послідовно впорядковує додавання й
дає id без пропусків (послідовність PG пропускає значення при відкаті, тому `sqlite_sequence`-перевірка тут не годиться). `verify()`
перевіряє ланцюжок, послідовність id й що `last_id`/`head_hash` збігаються з хвостом таблиці (відрізання хвоста видно).
Незмінність: тригер на UPDATE/DELETE плюс `REVOKE UPDATE, DELETE` для ролі застосунку. Ролі PostgreSQL: `dw_owner` (DDL, міграція,
лише для ручних операцій), `dw_app` (INSERT/SELECT, UPDATE лише на `incidents`, `incident_reviews`, `ha_lease`, `ha_epoch`,
`audit_head`).

### Збій PostgreSQL під час роботи лідера
Запис не вдався (таймаут, обрив, перемикання): тривога лишається на екрані й іде в `pending` (існуючий механізм), дії оператора
і зміни дають 503. **Запобіжник-вимикач**: після збою БД не чіпається N секунд, щоб повторні таймаути не тримали загальний
`engine.lock` і не зупиняли сканування. Повернення БД: `pending` дописується з дедуплікацією (існуючий `_flush_pending`).
Резерв при цьому лишається на `:memory:`; після підвищення відкриває PostgreSQL (як зараз відкриває файл).

### Redis Sentinel
`redis.sentinel.Sentinel(...).master_for(...)` для сесій, ліміту входів і релея. Збій, як і раніше, `SessionStoreError` (fail-closed).
Релей-підписник уже перестворює підписку при помилці: працює й після зміни master. Свідомі слабкості асинхронної реплікації
Redis: при перемиканні можна втратити кілька останніх сесій (користувачу треба перелогінитись) і скинути вікно ліміту входів
(коротке послаблення захисту від перебору). Прийнятно: на шлях запису тривог Redis більше не впливає.

### Міграція
`dronewatch-db-migrate --from incidents.db --dsn ...`: переносить `incidents`, `incident_reviews`, `incident_replays`, `audit_log`
з тими самими id й хешами (без перерахунку), виставляє `audit_head` і `IDENTITY` після максимального id, `ha_epoch` не нижче
файлового. Потім запускає перевірку ланцюжка в PostgreSQL. Не змінює джерело. Відмова, якщо цільова БД не порожня.

### Розгортання
`deploy/ha-cluster/`: окремі compose-файли для `node-a`, `node-b`, `witness`, шаблони конфігів Patroni, etcd, Sentinel,
Redis, сертифікати (скрипт, що розширює існуючий `certs`). Образ Patroni збираємо самі (postgres + patroni[etcd3]); Spilo відхилено
як надто важкий. Усі сервіси слухають лише на адресі WireGuard-інтерфейсу; README дає приклад mesh WireGuard між трьома VPS
і правила фаєрвола. TLS на PostgreSQL, Redis, Sentinel, etcd (клієнтський і peer) увімкнено завжди, поверх WireGuard.
Репетиція: профіль `ha-cluster-sim` піднімає всі ролі на одній машині в окремих мережах; `scripts/ha_failover_drill.*`
вбиває вузол, міряє час до відновлення запису й перевіряє, що дублів тривог нема.

## Тести
- Юніт адаптера: однакові сценарії на SQLite і PostgreSQL (пропускаються без `DRONEWATCH_TEST_PG_DSN`); CI додає сервіс postgres:16.
- Оренда й запобіжник у PostgreSQL: захоплення, поновлення, закінчення за годинником БД, два конкурентні acquire (рівно один виграє),
  старий epoch відмовлений на записі, `FOR SHARE` не дає записати після підвищення іншого.
- Журнал: ланцюжок, відрізаний хвіст, спроба UPDATE/DELETE під роллю `dw_app` відмовлена.
- Збій БД під час роботи: тривога в `pending`, вимикач не тримає `engine.lock`, дописування після повернення без дублів.
- Fail-closed: немає пакета psycopg, немає PostgreSQL при старті HA, `sslmode` слабший за `verify-full`, Redis без TLS.
- Міграція: round-trip з реальним `incidents.db`, `verify` зелений, повторний запуск відмовлено.
- Вручну: репетиція на `ha-cluster-sim` і на справжніх трьох VPS: kill -9 лідера, вимкнення VPS цілком, відрізання одного VPS
  від мережі (не має бути двох писачів).

## Відкриті питання (лише для користувача)
1. ~~Як датчики потрапляють на вузол?~~ РІШЕНО користувачем: датчик публікує в обидва брокери (по одному на VPS-A і VPS-B).
   Standby отримує події напряму зі свого брокера. Наслідки для виконавця: документація й приклад конфігу датчика з двома
   брокерами; дедуплікація не потрібна (трекер і так приймає дублі ідемпотентно, перевірити тестом); сам код датчиків поза межами.
2. **Синхронна реплікація PostgreSQL.** `synchronous_mode` Patroni без `strict`: при смерті репліки master пише далі (можлива
   втрата кількох останніх записів при подальшому падінні master). `strict`: master відмовляє у записі, поки нема синхронної
   репліки (тривоги йдуть у `pending`, на екрані є, у журнал не пишуться). Мій вибір: без `strict`.

## Що лишається будівельнику
Точні імена таблиць і ролей, межі пулу з'єднань, N секунд вимикача, версії образів, формат скрипта репетиції, чи залишити v1
(`lease_store: redis`) після стабілізації.
