# Активний рушій і гарячий резерв (HA, design, security-first)

## Навіщо
Зараз рушій один на процес: `Tracker`, стан треків, SQLite (інциденти, журнал дій), підписка MQTT. Падіння процесу чи вузла
лишає систему сліпою, а це система тривог. Мета: кілька копій сервісу, з яких працює одна, а решта миттєво її підміняє.
У Redis зараз лише сесії й ліміт входів (`dashboard.session_store: redis`); решта стану на процес.

## Принципи (мають силу над рештою рішень)
1. **Не більше одного, хто пише.** Інциденти, перегляди, журнал дій з ланцюжком хешів і розстановка змінюються лише з
   чинною орендою. Дві копії, що пишуть, ламають ланцюжок хешів, тож це гірше за паузу.
2. **Тривога важливіша за запис.** Втрата Redis чи оренди не повинна глушити показ тривоги оператору (див. «Деградація»).
3. **Fail-closed для змін.** Немає чинної оренди: жодних дій оператора й адміна, жодних записів у БД.
4. **Одна копія для людей.** Дашборд, API й WebSocket віддає лише лідер. Резерв не показує власних треків: їхні номери
   відрізнялися б від треків лідера, і review тривоги йшов би не туди.

## Цілі
- Падіння лідера: резерв стає лідером за ≤ `lease_ttl_s` (за замовчуванням 6 с), без втрати журналу.
- Резерв гарячий: уже має живі треки, тому після підміни не потрібен новий розгін (`min_age_s`) і не буде шторму повторних тривог.
- Одна копія без HA працює як раніше (HA вмикається конфігом).

## Не цілі
- Горизонтальне масштабування одного трекера (він неподільний: один дрон має бути одним треком).
- Шардинг за територією (можливий вже зараз окремими розгортаннями).
- Багато активних копій з показом (активно-активна схема).
- Резервування самого Redis і брокера MQTT.

## Підходи (для довідки; обрано 1)
1. **Активний + гарячий резерв з орендою в Redis (обрано).** Мало нового коду, зберігає інваріант «один трекер».
2. Один рушій + багато веб-процесів: рушій лишається єдиною точкою відмови, бракує того, що просили.
3. Шардинг за територією: не дає надійності, нічого не будує в коді.

## Дизайн

### Оренда й запобіжник
- Ключ `dw:leader` у Redis: значення `<instance_id>:<epoch>`. `epoch` береться з `INCR dw:epoch` при кожному захопленні, тож зростає.
- Захоплення: `SET dw:leader <id>:<epoch> NX PX ttl`. Поновлення кожні `ttl/3` скриптом (поновити лише якщо значення моє).
- Лідер сам відраховує свій термін за монотонним годинником від **початку** запиту на поновлення. Не встиг поновити до цього
  терміну (Redis недоступний чи повільний): лідер вважає, що оренди нема, ще до того, як ключ може перехопити інший.
- `epoch` додається в кожен запис БД і журналу дій. Старий лідер, що ожив, бачить більший epoch і відмовляється писати.

### Що робить кожна роль
| | лідер | резерв |
|---|---|---|
| MQTT і прийом подій | так | так (слухає ті самі події) |
| Трекер, `tick()` | так | так, без побічних ефектів |
| Запис в БД, журнал дій | так | **ні** |
| HTTP/WS для людей, `/api/events` | так (`/readyz` = 200) | ні (`/readyz` = 503) |
| Нова розстановка, review, ask AI | так | ні |

- Балансувальник/проксі ходить на `/readyz`: лише лідер приймає трафік. Датчики з HTTP шлють на лідера.
- Побічні ефекти в `tick()` (INSERT інциденту, AI-індексація, replay, broadcast) стоять за одним прапорцем `active`.
  Це єдине місце, яке міняє `engine.py`; трекер і фільтр не чіпаються.

### Події в резерві
- MQTT: кожна копія підписана сама. **Потрібен унікальний `client_id` на копію.** Зараз він дорівнює `username`
  ([mqtt_in.py](../../../src/dronewatch/service/mqtt_in.py), `client_id=username or "dronewatch-service"`): дві копії з одним
  `client_id` постійно вибивали б одна одну з брокера. Лишається один `username` (ACL брокера не міняється), `client_id`
  отримує суфікс `instance_id`.
- HTTP `POST /api/events` приймає лише лідер. Прийняті події лідер дублює в Redis-канал `dw:events` (best-effort, як QoS 0),
  резерв їх споживає. Події, прийняті резервом з MQTT, не дублюються: резерв бере їх із брокера сам.

### Перемикання
- Резерв отримує оренду: `active = True`, відкриває БД на запис, перевіряє ланцюжок журналу (як при старті), стає `ready`.
- **Тривоги, підняті резервом до підміни,** не губляться: резерв тримає обмежений список (`max 200`) тривог без запису.
  При підвищенні кожна з них пишеться як інцидент із приміткою `raised during failover`.
- Клієнти дашборда перепідключуються до нового лідера (WebSocket уже має перепідключення; перевірити).

### Деградація (оренда втрачена, Redis недоступний)
- Показ тривог **не вимикається**: лідер, що втратив оренду, лишається «скоріш за все єдиним» і далі шле тривоги своїм
  клієнтам з червоним банером «HA: оренда втрачена». Запис у БД і дії оператора при цьому відмовляють (503 для змін).
- Тривоги такого лідера йдуть у той самий обмежений список і записуються при поверненні оренди.

### Сховище (дивись відкрите питання 1)
- **v1 (обрано мною):** спільний файл SQLite на одному томі, відкритий на запис лише лідером. Захищає від падіння
  процесу й контейнера, не від втрати вузла.
- **v2 (окремо, за потреби):** PostgreSQL для інцидентів, переглядів, replay і журналу з ланцюжком хешів
  (head береться під блокуванням рядка). SQLite лишається типовим для однієї копії.

### Конфіг
```yaml
ha:
  enabled: false          # вимкнено: поведінка як раніше
  redis_url: ...          # той самий Redis, що для сесій (окремий префікс dw:)
  lease_ttl_s: 6
  instance_id: auto       # імʼя копії; авто = hostname
```
Без `ha.enabled` не змінюється нічого: новий код не виконується.

## Тести й перевірка
- Юніт: оренда на фейковому Redis (захоплення, поновлення, втрата, epoch росте, старий epoch відмовлений).
- Інтеграція: два Engine на одному потоці подій, лідер «падає», резерв піднімає ті самі треки без повторних тривог.
- Fail-closed: немає Redis при старті HA-режиму: сервіс не стартує, а не працює без HA мовчки.
- Перевірити окремо вручну: два справжніх процеси з Redis і брокером, `kill -9` лідера, секундомір.

## Відкриті питання (тільки для користувача)
1. Сховище: v1 (спільний SQLite на одному вузлі) чи одразу PostgreSQL?
2. Деградація: чи згоден ти, що без оренди тривоги показуються, а змінювати нічого не можна?

## Що лишається будівельнику
Точні назви метрик і логів, формат `/readyz`, тайм-аути Redis (за зразком `dashboard_redis.py`), як тестувати Redis без
справжнього сервера (fakeredis чи власна заглушка).
