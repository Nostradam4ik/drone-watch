# Ролі та журнал дій (design, security-first)

## Навіщо
Drone Watch захищає людей від дронів: тут не місце тихим дірам у доступі. Зараз усі, хто увійшов, мають однакові права, а дії
фіксуються лише частково. Потрібні розмежування прав і журнал, якому можна довіряти при розборі інциденту.

## Принципи (мають силу над рештою рішень)
1. **Fail-closed.** Немає ролі, невідома роль, збій журналу, невизначений стан: відмова, а не дозвіл.
2. **Сервер вирішує.** UI лише ховає кнопки; кожен ендпоінт перевіряє роль сам.
3. **Заборонено за замовчуванням.** Новий ендпоінт, що змінює стан і не оголосив роль, не може пройти тести.
4. **Журнал доводить, а не просить вірити.** Захист від змін на рівні БД плюс ланцюжок хешів із перевіркою.

## Цілі
- Ролі `viewer` < `operator` < `admin` (вкладені права).
- Журнал дій із виявленням підробки; запис виконується до дії.
- Існуючі розгортання не отримують неявних прав.

## Не цілі
- Керування користувачами й ролями з UI/API (ролі лише в конфігу).
- Окремі права на кожну дію.
- Спільне сховище сесій (окремий пункт roadmap).
- Зовнішнє якорення журналу (SIEM, WORM-сховище): див. «Обмеження».

## Підходи
1. **Упорядковані ролі + залежність `require_role(min)` (обрано).** Мало коду, легко перевірити повністю.
2. Набір прав на кожну дію: гнучкіше, але більше поверхні для помилок при трьох ролях.
3. Журнал у файлі: гірше, немає транзакцій із самою дією й тригерів захисту.

## Дизайн

### Ролі
- `dashboard.users[].role` ∈ {viewer, operator, admin}, **обов'язкове**. Немає чи невідоме: сервіс не стартує з чіткою
  помилкою (як і з порожнім списком користувачів при `auth: required`). **Наслідок:** існуючі конфіги треба один раз
  доповнити `role:`; це свідома ціна fail-closed (у документації й повідомленні про помилку є готовий рядок).
- Права:
  - viewer: читання стану, тривог, карти, сенсорів, покриття, WebSocket.
  - operator: плюс `POST /api/incidents/{id}/review`, `POST /api/ask`.
  - admin: плюс `PUT/DELETE /api/layout`, `POST /api/coverage`, `GET /api/audit`.
- `Session` несе `role`; `Users.authenticate` повертає роль або None. `/api/me` віддає `{user, role, auth}`.
- `require_role(min)` повертає 403 і пише в журнал `denied`. Невідома роль у сесії трактується як відмова.
- **Guard-тест:** обходить усі маршрути застосунку; будь-який POST/PUT/PATCH/DELETE без `require_role`/`require_user`
  (крім явного allowlist: login, logout, events із ключем датчика) валить CI.
- Режим `auth: disabled` (рішення користувача, 2026-11-22): анонім отримує **лише `viewer`**. Будь-яка зміна стану
  (підтвердження тривог, AI, розкладка, покриття, журнал) вимагає входу, тож без користувачів вона недоступна. Демо: якщо в
  конфігу є `dashboard.users`, вхід обов'язковий, як і в live; без користувачів демо лише для перегляду.
  Гучне попередження при старті лишається.

### Журнал
Таблиця `audit_log(id, ts, user, role, action, target, result, ip, prev_hash, hash)` у `incidents.db`.
- **Захист у БД:** SQLite-тригери `BEFORE UPDATE`/`BEFORE DELETE` з `RAISE(ABORT)`. API на зміну й видалення немає.
- **Ланцюжок:** `hash = SHA-256(prev_hash || канонічний запис)`; перший запис має фіксований початковий `prev_hash`.
  `dronewatch-audit --verify` перевіряє цілісність ланцюжка й повертає ненульовий код при розриві.
  Верифікація також запускається при старті сервісу: розрив = гучна помилка в лозі (старт не блокуємо: інцидент не має
  зупиняти захист), метрика/поле у `/api/health` для повного користувача.
- **Запис до дії (fail-closed):** для дій, що змінюють стан, спершу пишемо запис `result=started`/рішення, потім виконуємо;
  якщо запис у журнал не вдався, дія не виконується (503). Підтвердження тривоги пише журнал і зміну статусу в одній
  транзакції. Результат дії дописується окремим записом (`ok`/`error`), старі записи не змінюються.
- **Що пишемо:** `login`, `login_failed`, `logout`, `review`, `layout_save`, `layout_reset`, `coverage_set`, `denied`,
  `audit_read` (читання журналу теж дія). AI-запити не пишемо (лише читання, дуже багато).
- **Що не пишемо:** паролі, токени сесій, тіла розкладки/покриття (лише факт і ціль).
- **Недовірений ввід:** ім'я при невдалому вході, коментар, цілі: обрізання за довжиною, керівні символи вилучаються;
  UI показує лише через `textContent`.
- **Флуд:** `login_failed` ≤ ліміт `LoginLimiter` на адресу; відмови 429 агрегуються (один запис за вікно), щоб не
  роздувати БД.
- **IP:** `request.client.host`. `X-Forwarded-For` не довіряємо (підробляється); за reverse-proxy це адреса проксі,
  про що документуємо.
- `GET /api/audit?limit=` (admin; за замовчуванням 100, стеля 1000), найновіші першими. Автоматичного видалення немає.
- Існуюча `incident_reviews` лишається як є.

### UI
Кнопки підтвердження показуються від operator, редагування розкладки й покриття від admin. Для admin: вкладка
«Журнал дій» (таблиця з `/api/audit`, індикатор цілісності ланцюжка). Усе, що приходить із журналу, через `textContent`.

### Тести (обов'язкові)
- Матриця роль × ендпоінт (200/403/401) для кожного захищеного ендпоінта.
- Конфіг без `role` і з невідомою роллю не стартує.
- Журнал: запис для кожної дії й відмови; UPDATE/DELETE по `audit_log` відхиляються БД; зміна рядка «в обхід»
  (вимкнені тригери) виявляється `--verify`; збій запису блокує дію; флуд-ліміт; ін'єкція в ім'я/коментар.
- Guard-тест на всі маршрути; WebSocket не віддає більше, ніж viewer.
- Браузерні: viewer не бачить кнопок operator/admin, admin бачить журнал.
- Перед злиттям: окремий security-огляд diff (/code-review) і запуск повного набору перевірок.

## Обмеження (чесно)
Той, хто має запис у файл `incidents.db` (доступ до машини), може переписати журнал разом із ланцюжком; перевірка
це виявить лише якщо збережено останній хеш окремо. Якорення хешу зовні (SIEM, друк у syslog) лишається окремим кроком.
Журнал доводить цілісність, але не захищає від компрометації самого хоста.

## Лишається виконавцю
Тексти UI, формат часу, індекс по `ts`, точний формат канонічного запису для хешу.
