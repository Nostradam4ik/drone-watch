# Drone Watch

[![CI](https://github.com/Nostradam4ik/drone-watch/actions/workflows/ci.yml/badge.svg?branch=main)](https://github.com/Nostradam4ik/drone-watch/actions/workflows/ci.yml)

Мультидатчикове виявлення дронів: fusion-трекер (EKF + IMM, гейтинг за Махаланобісом, угорський алгоритм), HTTP/WebSocket-сервіс
із дашбордом, емулятор датчиків і Docker-стенд із брокером MQTT.

## Структура репозиторію

    src/dronewatch/
        fusion/      алгоритм: моделі, трекер, симулятор і візуалізація (python -m dronewatch.fusion.run)
        service/     FastAPI-сервіс: engine, автентифікація, дашборд, MQTT, конфіги та static/ (точки входу: dronewatch-serve, -keygen, -audit, -bench)
        service/ai/  AI-асистент оператора: клієнт Mistral, RAG-індекс на Qdrant, тули, агент (розділ нижче)
        emulator/    емулятор датчиків (лише стандартна бібліотека; dronewatch-emulate)
    tests/           pytest (імпортують встановлений пакет)
    docker/          Dockerfile сервісу й емулятора (збирати з кореня репозиторію)
    deploy/          демо-конфіг, брокер (mosquitto.*), генератор сертифікатів
    docs/images/     скріншоти

## Запуск

Python 3.12+. Пакет встановлюється з кореня репозиторію (src-layout: без встановлення `dronewatch` не імпортується):

    pip install -e ".[dev]"      # залежності сервісу й pytest, ruff, mypy, httpx, cryptography
    pytest                       # усі тести
    ruff check .                 # лінтер
    mypy                         # перевірка типів (каталог src)

Дашборд у справжньому браузері (Playwright + Chromium; без них ці тести просто пропускаються):

    pip install -e ".[dev,browser]" && python -m playwright install chromium
    pytest -m browser            # сторінка, тривоги, рішення оператора, тости, екранування, AI-панель

Код дашборда: `service/static/index.html` (лише розмітка) і `service/static/app/` (стилі та JS за темами: core, map,
viewer3d, dossier, panels, sound, editor, audit, main). Це ES-модулі: `index.html` підключає лише `main.js`, решту він тягне
через `import`. Спільний змінний стан (`cfg`, `state`, `selected`, `map`, стан редактора) лежить в об'єкті `S` у `core.js`:
модуль не може переприсвоїти чужу змінну. Бібліотеки `maplibregl` і `pmtiles` лишаються звичайними глобальними скриптами. Новий файл треба також додати в `APP_FILES` (app.py),
інакше сервер його не віддасть (тест `test_app_dir_has_no_unlisted_files` про це нагадає).

Демо-режим по відкритому HTTP (лише для localhost: ключі й стан ідуть без шифрування):

    python -m uvicorn dronewatch.service.app:app --port 8000

Далі відкрити http://127.0.0.1:8000.

Бойовий запуск і Docker: HTTPS через `python -m dronewatch.service.serve` (або `dronewatch-serve`) з `TLS_CERT_FILE`/`TLS_KEY_FILE`
(без них не стартує), див. розділ «HTTPS для API, дашборда і WebSocket». `docker compose up --build` піднімає все з демо-сертифікатами:
https://localhost:8000. Вхід у дашборд: користувач `demo`, пароль у `docker-compose.yml` (змінна
`DRONEWATCH_DASHBOARD_PASSWORD` сервісу `emulator`; демо-секрет, публічний). Деталі: розділ «Вхід у дашборд».
AI-асистент у дашборді — окремий профіль `ai`, розділ «AI-асистент оператора» нижче (перед показом дайте
емулятору прогнати кілька сценаріїв, щоб RAG-пошук мав що знаходити).

## Конфігурація

Усе налаштовується у YAML, код чіпати не треба. Конфіги лежать у пакеті й їдуть разом із ним.

- [config.yaml](src/dronewatch/service/config.yaml): активний конфіг. За замовчуванням `mode: demo` (вбудований симулятор рою).
- [config.example.yaml](src/dronewatch/service/config.example.yaml): приклад бойового режиму з коментарями до кожного поля.

Свій конфіг: `CONFIG=шлях/до/файлу.yaml python -m uvicorn dronewatch.service.app:app --port 8000`.
У `mode: live` симулятора немає, події приходять на `POST /api/events`.
У `mode: demo` блок `sensors` ігнорується (датчики бере симулятор), зони й параметри тривог читаються з конфігу.

Конфіг перевіряється при старті: невідомий тип датчика, дублікати id, відʼємна дальність, відсутні зони чи відсутній
радар (за відсутності двох пеленгових датчиків) дають зрозуміле повідомлення про помилку, а не мовчазну поламку.

## Карта дашборда (оффлайн, без зовнішніх запитів)

Дашборд показує реальну 3D-карту навколо об'єкта (MapLibre). Де саме на Землі лежить точка (0, 0) координат датчиків
(position у метрах: схід, північ), задає `origin: {lat, lon}` у конфігу (за замовчуванням Ейфелева вежа, Париж).

Карта лежить **в одному власному файлі**, а не береться з чужого сервера: сторонній сервер тайлів бачить, яку ділянку розглядає
оператор, і карта зникає без інтернету. Файл створюється раз, там, де є інтернет:

    pip install -e ".[map]"
    dronewatch-mapbuild --lat 48.8584 --lon 2.2945 --radius-km 12 --out data/map/paris.pmtiles   # ~60 МБ, 3 хвилини

Сервіс сам знаходить `data/map/paris.pmtiles` (шлях задає `map.pmtiles`; у docker-compose теку `./data/map` змонтовано
в контейнер). Режим карти видно в `/api/config`:

- **offline**: є власний файл, жодних зовнішніх запитів (карта, підписи й шрифти віддає сам сервіс; файл карти потребує входу);
- **online**: файлу немає, але в конфігу свідомо `map.online_tiles: true`: тайли тоді йдуть з OpenFreeMap, і він бачить ділянку;
- **none** (за замовчуванням без файлу): підкладки немає, працюють лише зони, датчики й цілі.

Дані: © OpenStreetMap contributors (ODbL), збірка Protomaps. Шрифти: Noto Sans, Space Grotesk, JetBrains Mono (SIL OFL).

## Розстановка датчиків на карті (лише demo)

У `mode: demo` кнопка «✎ Розставити» біля заголовка «Датчики» вмикає редактор: оберіть тип і клікніть по карті, щоб поставити
датчик; тягніть датчик мишею, щоб пересунути; `×` у списку прибирає; «Скинути» повертає вбудовані. Зони тут виводяться з радарів
(у demo зони з конфігу не читаються): навколо кожного радара буферна (40 % його дальності, «увага») і критична (1/6 дальності,
«загроза»); для радара на 1500 м це 600 і 250 м. Радар додали, пересунули чи прибрали: його зони з'являються, їдуть чи зникають.
Без радарів (лише пеленгові датчики) стоять зони 600 і 250 м навколо центра датчиків.

Буферна зона підсвічується покриттям завжди, і в demo, і в бойовому режимі (`GET /api/coverage` для поточних датчиків, `POST` для
розстановки, що ще тягнеться в редакторі; рахує сервер; вимикається галочкою в легенді): **повне** (радар + тріангуляція
пеленгами чи другий радар + RF-ідентифікація), **добре** (є радар: позиція й висота), **слабке** (лише пеленгові датчики: грубо,
без висоти) і **сліпа** зона. Пеленги вважаються надійними, якщо перетинаються під кутом від 20°; датчики на одній лінії з ціллю
дають лише «добре». Збоку виводяться відсотки зони для кожного класу й частка, де RF може визначити модель дрона.

**Будинки на лінії видимості.** Якщо є файл контурів будинків, радар і RF бачать ціль лише тоді, коли між ними й ціллю (на висоті
`map.target_alt_m`, 30 м за замовчуванням) немає вищого будинку; клітинки за будинками стають слабшими чи сліпими. Файл робиться з
тієї ж оффлайн-карти, нових завантажень немає:

    dronewatch-buildings --pmtiles data/map/paris.pmtiles --out data/map/buildings.npz   # ~40 МБ, пів хвилини

Висота датчика над землею береться з третьої координати `position: [схід, північ, висота]` (у редакторі це поле `height`);
радар на даху чи щоглі бачить над нижчими будинками. Межі моделі: двори й дерева не враховані;
у більшості будинків OSM не знає висоти, і їм ставиться припущена (10 м, видно в підсумку інструмента), тож це оцінка, а не гарантія;
акустичні датчики не затуляються (звук огинає будинки). Без файлу покриття рахується як раніше, а відповідь має `los: false`, і
редактор пише, що будинки не враховано. Лише підсвітка покриття: трекер правило «радар мав побачити» від будинків не залежить.

**Рельєф.** Окремий файл висот землі, так само раз і оффлайн (потрібен інтернет лише для завантаження):

    dronewatch-dem --lat 48.8584 --lon 2.2945 --radius-km 12 --out data/map/dem.npz   # ~2,5 МБ, кілька секунд

Джерело: відкриті тайли Terrarium (AWS Open Data, збірка Mapzen: SRTM NASA/USGS, GMTED2010, національні моделі висот), ~25 м на піксель
на 12-му масштабі; сервіс (`map.dem`) читає файл лише через numpy. З ним промінь, що пішов би під землю, закритий: пагорб затуляє
те, що за ним, а радар на вершині бачить униз по схилах. Будинки стоять на землі (висота даху = земля + висота будинку), тож разом
вони рахуються правильно. Висота датчика й цілі відлічується від землі в їхній точці. Точність висот десь ±5-10 м (у місті SRTM
показує й дахи), кривизна Землі не враховується (~0,3 м на 2 км). **Поза файлом висота невідома, і видимість там закрита**
(краще не обіцяти покриття, ніж пообіцяти зайве): датчик поза файлом нічого не покриває. Радіус файлу має охоплювати зони й сенсори.
Для Парижа ефект малий (місто пласке: різниця висот ~100 м на 12 км), для пагорбів і гір він основний.

**Реальні моделі.** У групі «Реальні моделі» палітра містить радари з опублікованими характеристиками: Robin Radar IRIS, Echodyne
EchoGuard, Blighter A422 (180°) і A402 (90°). Їхні даташити лежать локально в `docs/datasheets/` (теку виключено з git: PDF не комітяться, джерела вказано в `sources`). Правило каталогу (`SENSOR_TYPES`, поле
`real`, перевіряється `tests/test_catalog.py`): кожен параметр симуляції (дальність, сектор, точність, ймовірність виявлення, хибні
спрацювання) або підтверджений даташитом (`known`), або позначений припущенням (`assumed`), і дашборд показує це поруч із
джерелами. Що даташит вказує, але симуляція не моделює (кут місця, частота оновлення, класифікація), лежить в `extra`.
`max_range` у реальних моделей це дальність виявлення малого дрона з даташита (де вона є), а не технічна дальність радара. Це
часто нижня межа («понад 1 км»), тож реальна може бути іншою. Щоб додати модель, покладіть її даташит у `docs/datasheets/` (локально) і
вносьте лише те, що в ньому є.

**Сектор огляду.** Датчик може дивитися не навколо себе, а в сектор: `heading` (куди, компасні градуси, північ = 0) і ширина `fov_deg`.
Поза сектором він нічого не бачить ні в симуляції, ні в підсвітці покриття, а трекер не чекає від нього підтвердження цілі. У
редакторі секторний датчик має білу ручку на осі огляду: тягніть її, щоб повернути. У палітрі є узагальнений «Радар секторний 120°»
(параметри як у середнього; це не конкретна модель). У `mode: live` сектор задається в конфігу: `heading_deg` і `fov_deg` біля
датчика (за замовчуванням 360, тобто круговий огляд); емулятор бере їх з `/api/config`. Типи: радар дальній
(3000 м, груба точність), середній (1500 м), ближній (800 м, точний), RF-детектор, акустичний. Кожна зміна це повна нова розстановка
(`PUT /api/layout`, `DELETE /api/layout` повертає вбудовану): сервер перевіряє її (до 12 датчиків, до 5 км від центру, потрібен
щонайменше один радар або два пеленгові), перезапускає симуляцію й починає новий сеанс трекінгу. Датчики з палітри ідеальні: без
зсувів і затримок. У `mode: live` розстановка недоступна (409): там датчики мають ключі й ACL брокера та задаються конфігом.

Запуск у Docker: `docker compose --profile sandbox up -d --build` піднімає demo на https://localhost:8001 (профіль `sandbox`, конфіг
`deploy/config.demo.yaml`, без користувачів: лише перегляд) поруч з основним бойовим сервісом на 8000. Без Docker: `python -m uvicorn
dronewatch.service.app:app --port 8001` (demo із `src/dronewatch/service/config.yaml`).

## API

| Метод | Шлях | Призначення |
|---|---|---|
| POST | `/api/events` | пакет детекцій від датчиків (формат нижче) |
| GET | `/api/state` | поточні треки і стан датчиків |
| GET | `/api/sensors` | здоровʼя датчиків: `OK` / `WAITING` / `LOST` |
| GET | `/api/config` | датчики й зони |
| GET | `/api/incidents` | журнал тривог (SQLite; `DB_PATH`, за замовчуванням `./data/incidents.db`); `?status=new\|confirmed\|dismissed` |
| POST | `/api/incidents/{id}/review` | рішення оператора `{status, note?}`: підтвердити/відхилити (автор із сесії, історія зберігається). Рішення лише позначає тривогу: не пригнічує майбутні тривоги, трекер чи зони |
| GET | `/api/incidents/{id}/replay` | запис для відтворення інциденту (кадри цілей до й після тривоги, розстановка датчиків і зони на той момент); 404, якщо запису немає |
| GET | `/api/audit` | журнал дій (лише admin): `?limit=` 1..1000, за замовчуванням 100, найновіші першими |
| WS | `/ws` | потік стану 2 рази на секунду |

Формат події (азимут компасний, від півночі за годинниковою стрілкою):

    {"sensor_id": "radar1", "ts": 1760000000.5, "azimuth_deg": 212.0, "range_m": 640.0, "elevation_deg": 4.5}

Для пеленгових датчиків (RF, акустика) достатньо `sensor_id`, `ts`, `azimuth_deg`.
Події старші за 2 с відкидаються.

## Відтворення інцидентів

На картці тривоги кнопка «▶ Відтворити» показує на тій самій карті, що робили всі цілі за хвилину до тривоги й хвилину після
неї: повзунок часу, пауза, ×1/×4, Esc або «Закрити» повертає живий вигляд. Під час відтворення живі тривоги, тости й звук
лишаються активними. Лише читання (роль viewer), у журнал дій не пишеться.

Рушій тримає в памʼяті кільцевий буфер кадрів (раз на `step_s`, усі підтверджені цілі: положення, швидкість, рівень,
приналежність). Коли спрацьовує тривога, знімок за `before_s` одразу пишеться в таблицю `incident_replays` (щоб збій не з'їв
запис) і дописується ще `after_s` секунд; разом із кадрами зберігаються розстановка датчиків і зони на момент інциденту. У
спокійний час нічого не пишеться. Блок обмежений (кадри, до 100 цілей у кадрі), записи старші за `retention_days` прибираються.
Збій запису лише логується: трекінг не страждає. Інциденти, що були до цієї можливості, запису не мають (кнопка скаже про це).

    replay:
      enabled: true
      before_s: 60
      after_s: 60
      step_s: 1.0
      retention_days: 30

## Журнал дій

Окрема таблиця `audit_log` у тому самому `incidents.db`: хто (імʼя, роль), коли, що зробив, над чим, з яким результатом і з
якої адреси. Пишуться `login`, `login_failed`, `login_blocked`, `logout`, `review`, `layout_save`, `layout_reset`, `audit_read`
(читання журналу теж дія) і `denied` (спроба без потрібної ролі). Не пишуться паролі, токени сесій, тіла розкладки, питання до AI
та перегляд `POST /api/coverage` (він нічого не змінює). Читає лише admin: `GET /api/audit` або вкладка «Журнал дій» у дашборді.

- **Запис до дії (fail-closed).** Зміну стану спершу записують у журнал, потім виконують. Не вдалося записати: дії немає, 503.
  Підтвердження тривоги пишеться в одній транзакції зі зміною статусу. Відмови, невдалі входи й вихід пишуться «як вийде»: збій
  журналу лише логується, відповідь від цього не стає небезпечнішою.
- **Лише дописування.** Тригери SQLite забороняють UPDATE і DELETE. Рядки звʼязані ланцюжком SHA-256 (кожен хешує попередній),
  тож зміну чи видалення рядка помітно, навіть якщо тригери зняли напряму у файлі БД. Видалення з кінця й повне очищення видно
  з лічильника `AUTOINCREMENT` (id мають іти підряд від 1 до значення в `sqlite_sequence`).
- **Перевірка цілісності:** `dronewatch-audit --verify [--db ШЛЯХ]` (БД лише для читання; код 0 цілий, 1 пошкоджений з id першого
  невідповідного запису, 2 немає файлу чи таблиці). Те саме сервіс робить один раз при старті: пошкоджений журнал **не зупиняє**
  сервіс (захист від дронів важливіший), але пишеться `ERROR`, а `/api/health` для користувача з входом віддає
  `audit: {ok, rows, broken_at}`. Це результат старту, а не перевірка щоразу (перевірка проходить усю таблицю), тож вкладка в
  дашборді пише «цілий на момент старту»; актуальну перевірку дає `dronewatch-audit --verify`.
- **Недовірений ввід:** імена, цілі й коментарі обрізаються за довжиною, керівні символи вилучаються; дашборд показує їх лише
  через `textContent`.
- **Флуд:** рядки `login_failed` мають спільну стелю 30 за хвилину на всі адреси разом, понад неї один зведений рядок
  `login_failed_flood` за хвилину (кожна спроба все одно потрапляє в лог). Ліміт входів `LoginLimiter` рахує IPv6 за мережею /64.
  `denied` агрегується: один рядок на пару адреса (/64) плюс імʼя за 5 хвилин, зі спільною стелею 30 за хвилину і зведеним рядком
  `denied_flood`; `login_blocked` один на адресу (/64) за вікно.

**Обмеження журналу.**
- Хто має запис у файл БД, може **переписати ланцюжок цілком** (перерахувати всі хеші): ланцюжок виявляє зміну окремих рядків, а
  не підміну всього журналу. Для сильнішого захисту зберігайте `head` з `--verify` окремо (в іншому місці) і звіряйте.
- Автоматичного видалення й архівації немає: таблиця росте (темп обмежено стелею вище, але за диском стежте самі). Стеля 1000 рядків діє лише на одне читання.
- Запис ok/error після дії «як вийде»: якщо є `started` без підсумку, процес міг упасти посередині.
- IP: див. обмеження входу (за reverse proxy це адреса проксі).
- Журнал лежить у тому самому файлі, що й інциденти: резервна копія й права доступу ті самі.

## Стан датчиків і відмова радара

Сервіс стежить, коли від кожного датчика востаннє щось приходило. Мовчить довше за `sensor_timeout_s` (за замовчуванням 5 с)
і стан `LOST`: дашборд показує банер і червоний датчик, `/api/health` повертає `degraded: true` та `lost_sensors`.

Що змінюється при відмові радара: правила «ціль у зоні радара обовʼязково має радарне підтвердження» вимикаються,
і трек, який тримають RF та акустика, не видаляється. Позиція тоді рахується лише з пеленгів, тож похибка зростає
з одиниць метрів до десятків (на дашборді видно по колонці похибки треку). Коли радар повертається, правила вмикаються назад.

**Heartbeat.** Без нього «небо порожнє» і «датчик помер» не відрізнити. Тому кожен датчик має слати кожен скан
`{"sensor_id": "radar1", "heartbeat": true}` (HTTP або MQTT), навіть коли нічого не бачить. Датчик без heartbeat
теж працює, але в тихий період може показатися як `LOST`, а скан, у якому радар не озвався зовсім, не вважається
«радар не побачив ціль». Демо й емулятор шлють heartbeat самі (емулятор: `--no-heartbeat` вимикає).

## Резерв (HA): активний рушій і гарячий резерв

Кілька копій сервісу, з яких працює одна. Решта це гарячі резерви: слухають ті самі події й мають живі треки, але нічого не пишуть
і людям нічого не показують. Якщо лідер падає, резерв стає лідером за ≤ `lease_ttl_s` (6 с) і не підіймає повторних тривог.
Це **не горизонтальне масштабування**: трекер один (один дрон = один трек), копії лише страхують одна одну.

```yaml
ha:
  enabled: true                       # лише з mode: live; за замовчуванням false (одна копія, поведінка як раніше)
  redis_url: rediss://redis.internal  # redis:// дозволений лише на localhost (як для сесій); пароль краще в DRONEWATCH_HA_REDIS_URL
  lease_ttl_s: 6                      # 2..60
  instance_id: auto                   # hostname; HA_INSTANCE_ID у середовищі перекриває (копії з одним hostname)
```

**Як це працює.** Лідер тримає оренду в Redis (`dw:leader`, `dw:epoch`) і поновлює її кожні `ttl/3`. Термін він відлічує сам, за
монотонним годинником, тож перестає вважати себе лідером раніше, ніж оренду може перехопити інший. `epoch` зростає при кожному
захопленні й записаний у самому файлі БД (`ha_epoch`): лідер, що ожив після паузи, бачить новіший epoch і не може писати.
Тривоги, підняті резервом до підміни, дописуються як інциденти з `failover = 1`; ті, що лідер уже записав, дублів не дають.

| | лідер | резерв | лідер без оренди (DEGRADED) |
|---|---|---|---|
| MQTT, трекер | так | так | так |
| запис у БД, журнал дій, зміни | так | ні | **ні** (503) |
| дашборд, API, WebSocket | так | 503 | **перегляд так**, зміни 503 |
| `POST /api/events` | так | 503 (датчик ретраїть на лідера) | так |
| `/readyz` | 200 | 503 | 200 |

Балансувальник має дивитися на `/readyz` (лише там, де 200, люди бачать систему); `/api/health` відповідає всім копіям.
HTTP-події лідер дзеркалить у резерв через канал `dw:events` (без ключів датчиків; Redis має бути закритою внутрішньою мережею).

**Що треба в розгортанні:**
- **Власний логін брокера на кожну копію** (`dronewatch-service`, `dronewatch-service-2`, ...) і рядок ACL на кожен. Брокер ставить
  `client_id` рівним логіну (`use_username_as_clientid`), тож дві копії з одним логіном вибивали б одна одну безперервно.
  Логін копії задає `MQTT_USER`. Хеш: `dronewatch-keygen --mosquitto ІМ'Я ПАРОЛЬ`.
- Пакет `redis` (extra `dronewatch[redis]`; в образ docker він уже входить). Недоступний Redis при старті: сервіс не стартує.
- Один файл БД на всіх копіях (v1: спільний том на одному вузлі). Це захищає від падіння процесу й контейнера, **не від втрати
  вузла**. SQLite на мережевому диску не використовувати. Для багатовузлового розгортання знадобиться PostgreSQL (окрема робота).

**Обмеження, які варто знати:**
- Якщо Redis недоступний довше за `lease_ttl_s`, лідер переходить у DEGRADED: тривоги й далі показує, але змін не робить. Якщо
  сесії дашборда теж у цьому Redis (`dashboard.session_store: redis`), вхід і перегляд при його аварії відмовляють (503, fail-closed).
  Для кращої стійкості тримайте сесії й HA в окремих Redis.
- При розриві зв'язку з Redis готовими (`/readyz` 200) можуть бути одразу дві копії; стара не зможе писати (запобіжник epoch).
- Тривоги, що лідер у DEGRADED підняв, а оренду тим часом узяв інший, відкидаються з логом: новий лідер бачив ті самі події.

**Демо-стенд** (профіль `ha`): `docker compose --profile ha up -d --build certs mosquitto redis ha-a ha-b` (явно, без звичайного
`service`: він писав би в той самий том без оренди). Копія A: `https://localhost:8011`, B: `https://localhost:8012`. Redis і обидві
копії живуть в одному мережевому просторі, бо політика дозволяє `redis://` лише на localhost. Перевірка: `/readyz` на обох
(одна 200, інша 503), `docker kill saasfor-ha-<лідер>-1`, секундомір до 200 на другій (≈ 6-8 с), `dronewatch-audit --verify`.
Конфіг стенда `deploy/config.ha.yaml` це копія `deploy/config.yaml` плюс блок `ha`: датчики й зони правте в обох.

## Безпека входу

### Автентифікація датчиків (ключ на датчик)

У `live` кожна подія має нести чинний ключ **свого** датчика, інакше її відкидають (`stats.events_unauthorized`, на дашборді
бейдж «без чинного ключа»). Це стосується й heartbeat: підроблений «я живий» маскував би відмову справжнього датчика, тому
подія без ключа не зараховується навіть як ознака життя.

    dronewatch-keygen radar1 rf1 ac1       # ключ (покажіть лише датчику) і рядок key_sha256 для конфігу

    sensors:
      - id: radar1
        key_sha256: "86c5..."             # у лапках; сервер зберігає лише хеш, ключ відновити не може

- **HTTP:** заголовок `X-API-Key: <ключ>`. Ключ належить одному датчику: події інших датчиків у запиті відхиляються,
  а якщо не прийнято жодної через ключ, відповідь 401. Одному запиту, отже, один датчик.
- **MQTT:** поле `"key"` у кожній події: `{"sensor_id": "rf1", "key": "...", "ts": ..., "azimuth_deg": ...}`, а подія з
  топіка `dronewatch/events/<id>` має належати датчику `<id>`, інакше її відсікають (`events_unauthorized`).
- **Fail-closed:** у `live` без `key_sha256` у кожного датчика сервіс не стартує. Вимкнути можна лише свідомо:
  `auth: {mode: disabled}` (у лозі буде попередження). Демо-режим (`mode: demo`) без автентифікації.
- **Ротація:** новий ключ → замінити `key_sha256` і рядок у `deploy/mosquitto.passwd` → перезапустити сервіс і брокер → оновити датчик.
- Ключі й їхні значення не логуються й не повертаються в помилках.

### Брокер Mosquitto: логіни й ACL

Брокер у `docker-compose.yml` закритий: `allow_anonymous false`, вхід за логіном і паролем (`deploy/mosquitto.passwd`),
права за ACL (`deploy/mosquitto.acl`). Користувачі:

| Користувач | Пароль | Права |
|---|---|---|
| `radar1`, `rf1`, `ac1` (по одному на датчик) | ключ датчика, той самий, що в `X-API-Key` | **писати** лише в `dronewatch/events/<свій id>`, читати нічого |
| `dronewatch-service` | `MQTT_PASSWORD` сервісу | читати `dronewatch/events/#`, писати нічого |
| `healthcheck` | окремий | читати лише `$SYS/broker/uptime` |

Що це дає: датчик не може писати в чужий топік, читати події (отже й ключі) інших датчиків чи топіки `#`/`$SYS`, а чужа
людина без логіна взагалі не підключиться. `use_username_as_clientid true` не дає підключитися з чужим `client_id`
(наприклад, `dronewatch-service`) і витіснити того клієнта: брокер за специфікацією MQTT відключає наявного, але тепер
ім'я клієнта завжди дорівнює логіну, а логін чужий не підробиш.

Новий датчик: `dronewatch-keygen sensor9` дає ключ, рядок `key_sha256` для конфігу сервісу й рядок для `mosquitto.passwd`;
ACL правити не треба (правило `pattern write dronewatch/events/%u` діє на всіх датчиків за іменем користувача).
Після зміни `passwd`/`acl`: `docker compose restart mosquitto` (брокер копіює файли при старті з потрібними правами 0700,
бо інакше «майбутні версії відмовляться їх завантажити»).

Сервіс підключається користувачем зі змінних `MQTT_USER` / `MQTT_PASSWORD` (або `mqtt: {username, password}` у конфігу;
змінні оточення мають пріоритет). Хибний пароль сервіс пише в лог один раз (без самого пароля). **Увага:** Mosquitto
приймає підписку, яку ACL забороняє, мовчки й просто нічого не доставляє, тож хибну ACL по відповіді брокера не видно.
Симптом на дашборді: бейдж MQTT «подій немає N с (перевірте ACL)» за робочого зʼєднання (`mqtt.idle_s` у `/api/health`).

### TLS між брокером і клієнтами

Брокер слухає **лише TLS** (порт 8883); відкритого слухача 1883 немає зовсім. Логін, пароль, ключі датчиків і самі події
ходять зашифрованим каналом (TLS 1.2 або 1.3: версії 1.0 і 1.1 брокер відхиляє, перевірено).

Сервіс і емулятор довіряють **лише** CA брокера, а не всім системним, і завжди перевіряють сертифікат та ім'я хоста:
небезпечного режиму «не перевіряти» в коді немає. Чужий CA чи ім'я поза SAN відхиляються на рукостисканні, ще до передачі
логіна й пароля. Мінімальна версія клієнта TLS 1.2.

**Демо-сертифікати.** Їх створює сервіс `certs` (`deploy/gen-certs.sh`) у Docker-томах при першому `docker compose up`;
приватних ключів у репозиторії немає (це перевіряє тест). Томи розділені: `certs-ca` (лише публічний `ca.crt`) бачать
брокер, сервіс і емулятор, `certs-server` (`server.crt`, `server.key`) бачить лише брокер. Ключ CA ніде не зберігається:
CA одноразовий, підписує один сертифікат і зникає, тож ніхто не може випустити ще один, якому довіряють клієнти.
Перевипуск автоматичний, коли до кінця строку лишається менше 30 днів, змінилися SAN або файлів немає (а ще примусово:
`docker volume rm saasfor_certs-ca saasfor_certs-server`). Він створює новий CA, тому сервіс і емулятор мусять
перечитати `ca.crt`: `certs` стартує першим на кожен `docker compose up`, але уже запущені клієнти треба перезапустити.
Сертифікат видано на імена `mosquitto`, `localhost`, `127.0.0.1`; інші імена задає змінна `CERT_SANS` сервісу `certs`.

**Власні сертифікати (бойове розгортання).** Демо-CA одноразовий і непридатний для довіри між організаціями. Візьміть
сертифікат брокера від свого CA, ім'я хоста брокера має бути в його SAN (суворий режим X.509 у Python 3.13+ ще й вимагає
`authorityKeyIdentifier`). Покладіть `server.crt` і `server.key` туди, де їх читає брокер (`certfile`/`keyfile` у
`mosquitto.conf`; ключ тільки для читання власником `mosquitto`), а `ca.crt` дайте сервісу й датчикам.

Налаштування клієнтів:
- **Сервіс:** `MQTT_CA_CERT=/шлях/ca.crt` (або `mqtt.ca_cert` у конфігу) вмикає TLS із довірою лише цьому CA; `MQTT_TLS=1`
  (або `mqtt.tls: true`) без `ca_cert` довіряє системному сховищу. Порт задає `MQTT_PORT` (8883). Якщо задано логін,
  а TLS немає, сервіс пише попередження в лог, а бейдж на дашборді показує «без шифрування».
- **Емулятор:** `--mqtt-ca CA.PEM` або `--mqtt-tls`; `--mqtt` має містити ім'я з SAN (наприклад, `localhost:8883`).
- **З хоста:** `docker compose cp mosquitto:/mosquitto/certs-ca/ca.crt ./ca.crt`.
- Помилка TLS у сервісі (недовірений CA, ім'я поза SAN, брокер без TLS) пишеться в лог один раз з підказкою, без пароля.

### HTTPS для API, дашборда і WebSocket

У Docker сервіс обслуговує **лише HTTPS** (порт 8000): дашборд, REST API (`X-API-Key` для `POST /api/events`, стан,
тривоги) і WebSocket (`wss://`, фронтенд сам обирає його під `https:`). Відкритого слухача немає. Приймаються TLS 1.2 і 1.3
(1.0 і 1.1 відхиляються, перевірено).

Точка входу образу `serve.py` — **fail-closed**: без `TLS_CERT_FILE` і `TLS_KEY_FILE` сервіс не стартує, щоб ключі датчиків
випадково не пішли відкритим HTTP. Свідомо без шифрування (лише localhost або за власним TLS-проксі): `ALLOW_INSECURE_HTTP=1`
(у stderr буде попередження; прапорець працює лише зі значенням `1`). Образ навмисно не запускає `uvicorn` напряму в обхід
цієї перевірки.

Сертифікат сервісу створює той самий сервіс `certs` (`deploy/gen-certs.sh`), що й для брокера, але **окремий** (SAN `service`,
`localhost`, `127.0.0.1`) і в **окремому томі** `certs-http`: його ключ бачить лише сервіс, а ключ брокера (`certs-server`) лише
брокер. Сертифікат сервісу не годиться для імені брокера й навпаки (перевірено). Усе підписує той самий одноразовий CA.
Healthcheck контейнера (`healthcheck.py`) ходить по HTTPS і перевіряє сертифікат так само суворо, як клієнти.

**Клієнти.**
- **Емулятор:** `--url https://service:8000 --ca CA.PEM` (типова адреса тепер `https://127.0.0.1:8000`). Для сервісу в
  режимі розробки без TLS: `--url http://127.0.0.1:8000` (з попередженням, що ключі підуть відкритим текстом).
- **Браузер:** демо-CA йому невідомий, тому він покаже попередження про сертифікат. Додайте `ca.crt` до довірених
  (`docker compose cp service:/certs/ca.crt ./ca.crt`) або погодьтеся з винятком для цієї сторінки. Сертифікат у демо видано на
  `localhost` і `127.0.0.1`, тож відкривайте `https://localhost:8000` чи `https://127.0.0.1:8000`.
- **curl:** `curl --cacert ca.crt https://localhost:8000/api/health`. На Windows (schannel) додайте `--ssl-no-revoke`: curl
  там вимагає перевірки відкликання, а в демо-CA немає ні CRL, ні OCSP. Це вимикає лише перевірку відкликання, ланцюжок
  сертифікатів і ім'я хоста перевіряються як завжди.
- На Windows `localhost` клієнт спершу пробує як IPv6 `::1`, де сервіс не слухає, і може чекати ~2 с перед поверненням до IPv4.
  Події датчиків із міткою `ts` старшою за 2 с рушій відкидає, тож датчикам краще звертатися за `127.0.0.1` або за іменем
  із DNS.

**Власні сертифікати (бойове розгортання).** Покладіть сертифікат і ключ сервісу туди, де їх читає контейнер (`/tls/http.crt` і
`/tls/http.key`) або змініть `TLS_CERT_FILE`/`TLS_KEY_FILE`; ім'я хоста сервісу має бути в SAN, а сертифікат мати
`authorityKeyIdentifier` (суворий режим X.509 у Python 3.13+). Клієнтам видайте CA, яким його підписано. Замість вбудованого
TLS можна поставити перед сервісом reverse proxy (nginx, Caddy, Traefik) із `ALLOW_INSECURE_HTTP=1` лише на внутрішній
інтерфейс між проксі та сервісом: тоді проксі мусить передавати WebSocket (`Upgrade`) і сам відповідає за TLS.

**HSTS не додано навмисно.** Він діє на ім'я хоста без урахування порту й для `localhost` закрив би в браузері всі інші
ваші відкриті `localhost`-сервіси. Для справжнього доменного імені його варто ввімкнути на проксі.

### Вхід у дашборд (логін і пароль)

Стан, тривоги й WebSocket бачить лише той, хто увійшов. Це **окремі облікові дані від датчиків**: оператор не може слати
події, а ключ датчика не відкриває дашборд (перевірено тестом).

| Без входу | Після входу |
|---|---|
| `GET /` → 303 на `/login`; `/login` (форма) | `/`, `/api/state`, `/api/config`, `/api/sensors`, `/api/incidents`, `/api/me` |
| `/api/state` та інші читання → 401; `/ws` → 403 | `/ws` (WebSocket); `/api/health` із подробицями |
| `/api/health` → лише `{"ok": true}` (для healthcheck) | `POST /api/logout` |

`POST /api/events` сюди не належить: його захищає ключ датчика.

**Користувачі.** У конфігу лише scrypt-хеш пароля, самого пароля немає:

    dronewatch-keygen --dashboard-user operator --role operator            # пароль питає двічі (getpass), друкує рядок для конфігу
    dronewatch-keygen --dashboard-user operator --role operator --generate # випадковий пароль, показується один раз

    dashboard:
      auth: required          # за замовчуванням у live; disabled лише свідомо (у лозі попередження)
      session_ttl_s: 28800    # скільки діє сесія (8 годин)
      users:
        - {name: operator, role: operator, password_hash: "scrypt$16384$8$1$..."}

**Кілька процесів (спільні сесії).** За замовчуванням сесії й ліміт входів живуть у памʼяті одного процесу. Щоб кілька процесів
бачили одну сесію, поставте Redis: `pip install 'dronewatch[redis]'` і

    dashboard:
      session_store: redis
      redis_url: rediss://redis.internal:6380/0   # TLS; звичайний redis:// лише для localhost. Пароль краще в DRONEWATCH_REDIS_URL

Fail-closed: недоступний Redis при старті не дає сервісові піднятись; під час роботи вхід, перевірка сесії й WebSocket дають 503
(розсилка стану мовчить), а не «сесії нема» чи «ліміт вільний». Запасного сховища в памʼяті немає. У Redis лежить лише SHA-256
токена, строк сесії тримає TTL. **Межі:** це лише сесії та ліміт входів. Рушій (треки, тривоги, MQTT, SQLite з інцидентами та
журналом дій) лишається окремим у кожному процесі, тож кілька процесів без спільного рушія дають різні картини світу. Ліміти AI
й журналу теж на процес.

**Ролі.** Поле `role` обовʼязкове (без нього конфіг не завантажується, `--role` обовʼязковий і в `dronewatch-keygen`). Кожна
роль включає права нижчої:

| Роль | Може |
|---|---|
| `viewer` | читати стан, тривоги, датчики, інциденти, WebSocket; бачити підсумок рішення по тривозі |
| `operator` | + підтверджувати й відхиляти тривоги, питати AI-асистента |
| `admin` | + міняти розкладку датчиків і покриття (demo), читати журнал дій |

Сервер перевіряє роль на кожному маршруті (guard-тест валить CI, якщо маршрут без ролі); інтерфейс лише ховає недоступне.
Недостатня роль це 403 і запис `denied` у журналі. Без входу (demo без користувачів або свідоме `dashboard.auth: disabled`)
анонім отримує **лише viewer**: читає, але нічого не змінює. Невідома роль у сесії не дає нічого.

**Fail-closed:** у `live` без жодного користувача сервіс не стартує (повідомлення вказує на `dronewatch-keygen`). У `demo` з
користувачами в конфігу вхід теж обовʼязковий. Пароль не коротший за 12 символів (`dronewatch-keygen` коротшого не видасть).

**Як це захищено.**
- **Сесія:** довгий випадковий токен у cookie `dw_session` (`HttpOnly`, `SameSite=Strict`, `Secure` під HTTPS). На сервері лежить
  лише SHA-256 від токена. Сесії в памʼяті одного процесу: перезапуск виходить усіх; для кількох процесів потрібне спільне сховище.
  Вихід знищує сесію на сервері; WebSocket закривається за один скан (≤0,5 с). Скінчилась сесія, і її WebSocket теж закрито.
- **Підбір паролів:** не більше 8 спроб входу за 5 хвилин з однієї адреси (успішний вхід лічильник скидає), далі 429 із `Retry-After`;
  навіть правильний пароль не проходить, поки діє блокування. Спроба рахується атомарно ДО перевірки пароля, тож паралельний залп
  не обходить ліміт (перевірено: 30 одночасних запитів дають рівно 8 перевірок пароля й 22 відмови). Перевірка однаково дорога для існуючого й неіснуючого імені (за часом не видно, які імена є),
  а відповідь про помилку однакова. Довгі паролі відкидаються до хешування.
- **Підроблені запити з чужих сайтів:** вхід і вихід лише `application/json` (форма з чужого сайту так не відправляє), `Origin`,
  якщо він є, має збігатися з хостом (для WebSocket теж). Cookie `SameSite=Strict`.
- **Заголовки:** `Cache-Control: no-store`, `X-Frame-Options: DENY` і `frame-ancestors 'none'` (дашборд не вбудувати в чужу
  сторінку), `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`.
- **Журнал:** кожен вхід, вихід, невдала спроба й блокування (ім'я й адреса, без пароля; ім'я екрановано, переніс рядка не
  підробить запис). Докладно: розділ «Журнал дій» нижче.

**Обмеження.**
- Ліміт спроб рахується за адресою клієнта. За NAT чи reverse proxy всі клієнти виглядають однією адресою (у Docker це шлюз,
  `172.x.0.1`), тож один зловмисник може заблокувати вхід усім. За проксі задайте `FORWARDED_ALLOW_IPS` (лише тоді `dronewatch-serve` бере адресу з
  `X-Forwarded-For`), а проксі мусить сам перезаписувати цей заголовок.
- Зміна пароля чи ролі це нова команда `dronewatch-keygen`, правка конфігу й перезапуск сервісу (він виходить усіх).
- IP у журналі це `request.client.host`. Сам застосунок `X-Forwarded-For` не читає; `dronewatch-serve` вмикає розбір проксі-заголовків
  лише коли задано `FORWARDED_ALLOW_IPS` (довірені проксі). Без нього за reverse proxy в журналі адреса проксі.
- Схема API (`/openapi.json`, `/docs`, `/redoc`) вимкнена.
- Двофакторної автентифікації немає. Для відкритого в інтернет дашборда варто поставити перед сервісом проксі з SSO/VPN.
- Cookie `Secure` ставиться, коли запит прийшов по HTTPS; за проксі, що знімає TLS, задайте `COOKIE_SECURE=1`.
- Емулятор входить сам (`--dashboard-user ІМ'Я` і пароль у `DRONEWATCH_DASHBOARD_PASSWORD`, не в аргументах). Справжнім датчикам
  вхід не потрібен.

**Чого це не закриває.**
- Ключ датчика ще й у кожному MQTT-повідомленні (друга перевірка в сервісі, незалежна від налаштувань брокера). Канал
  шифрований, тож його не видно в мережі, але бачить сервіс і той, хто має його пароль у брокері. Замінити ключ у
  повідомленні підписом (HMAC) можна, але сервер тоді мусить зберігати сам ключ, а не його хеш.
- Клієнтські сертифікати (взаємний TLS) не вимагаються: клієнта автентифікують логін і пароль (брокер) та ключ (сервіс).
  Увімкнути можна окремо (`require_certificate true`), але це змінює видачу ключів датчикам.
- Паролі в `deploy/mosquitto.passwd` хешуються PBKDF2-SHA512 зі 101 ітерацією (формат фіксує сам брокер): для довгих
  випадкових ключів цього досить, для паролів, які вигадала людина, ні.
- Ключі й паролі в `deploy/config.yaml`, `deploy/mosquitto.passwd` і `docker-compose.yml` демонстраційні й публічні, а демо-CA
  одноразовий і непридатний для довіри між організаціями.

Тому `docker-compose.yml` за замовчуванням публікує порти 8000 і 8883 лише на `127.0.0.1`. Відкрити їх назовні (`0.0.0.0` або
адреса інтерфейсу) тепер можна, але лише після того, як: замінено всі демо-секрети (ключі датчиків, паролі брокера, користувач
дашборда), підставлено власні сертифікати (демо-CA непридатний) і перевірено обмеження вище, зокрема ліміт спроб за NAT.

Події недовірені (HTTP, MQTT), тому рушій відхиляє те, що не доходить до фільтра: нескінченні й NaN значення,
`range_m` поза `(0, 1,5 × max_range]`, `|elevation_deg| > 90`, `ts` старший за 2 с або на понад 2 с у майбутньому
(зсув годинників), нерядковий `sensor_id`. HTTP-схема забороняє `NaN`/`Infinity` (422 без відлуння значень).
Відхилене рахується в `stats.events_rejected`.

## Оцінка якості трекінгу на записах (OSPA, хибні треки)

`dronewatch-eval` подає запис подій датчиків у той самий `Engine`, що працює в сервісі (керований годинник, без мережі), і
рахує метрики. Міряється справжній код, а не окрема копія трекера.

    dronewatch-eval simulate --out rec/ --scenario swarm --seed 1                 # запис із симулятора (еталон відомий)
    dronewatch-eval run --events rec/events.jsonl --truth rec/truth.jsonl --sim-sensors ideal
    dronewatch-eval run --events flight.jsonl --truth gps.jsonl --config deploy/config.yaml --json report.json

**Формат запису**, JSONL, рядок = подія, як у `POST /api/events`: `sensor_id`, `ts`, `azimuth_deg`, `range_m`, `elevation_deg`
(за потреби `drone_model`, `heartbeat`). **Еталон** (де цілі були насправді), JSONL: `{"t": ts, "id": "gps1", "x": м, "y": м,
"z": м}` у системі координат датчиків (схід, північ, вгору від точки (0, 0)); між відліками лінійна інтерполяція, розрив довший
за `--max-gap` (5 с) робить ціль неактивною. `--truth-offset` виправляє зсув годинників. Запис без heartbeat: `--synthetic-heartbeat`.

**Метрики** (з еталоном): OSPA (`--cutoff` c, `-p`; складові положення й кількості окремо), RMSE, пропуски, частка хибних
треків (за номерами й за кадрами), перемикання ID, час до підтвердження. За замовчуванням порівнюється горизонталь (`--dim 2`):
висоту без радара трекер лише припускає. Без еталону рахується лише статистика треків (скільки, як довго жили, «мигаючі»), і звіт
прямо каже, що OSPA без еталону неможливий.

**Чесне обмеження:** справжніх записів датчиків у репозиторії немає. Усі цифри в тестах і прикладах походять із симулятора, тож
вони перевіряють сам інструмент і дозволяють порівнювати версії трекера, але НЕ є оцінкою на реальному обладнанні. Реальна
оцінка потребує запису з датчиків і еталона (наприклад, GPS-логу власного дрона). Формат вище підходить, лишається написати
конвертер вашого формату запису. Метрики тут рахуються по живих треках після `Engine.tick`, тому трохи відрізняються від
`python -m dronewatch.fusion.run` (той проганяє трекер напряму й міряє відстань у 3D).

## Потоп подій і потокобезпека

Усі зміни стану йдуть під одним замком `Engine.lock`: його беруть HTTP-потоки (`/api/events`, `/api/state`), потік MQTT
і цикл сканів. Валідація подій іде поза замком, а пакет потрапляє в буфер одним захопленням.

Буфер обмежений: `max_events_per_sensor_scan` подій від датчика за скан (за замовчуванням 150), `max_tracks` треків (200),
у тріангуляцію йде не більше 30 пеленгів від датчика за скан, а один `POST /api/events` не більший за 1000 подій
(інакше 422). Понад стелі події відкидаються й рахуються (`stats.events_dropped`, `tracks_capped`, `bearings_truncated`),
на дашборді зʼявляється бейдж «перевантаження». Без цих стель 300 випадкових подій на датчик давали скан до 27 с при
`scan_dt` 0,5 с; зі стелями найгірший виміряний скан був близько 1,1–1,5 с. Після оптимізації гейтингу (аналітичний якобіан, а `S`, `S⁻¹`
і `ln det S` рахуються раз на пару «трек × датчик» і весь рядок вартостей однією матричною операцією) це близько 0,03 с;
стелі можна піднімати (див. таблицю в `config.example.yaml`). Нормальний рій стелі не зачіпають.

**Заміряйте скан на цільовому залізі** перед тим, як підіймати стелі: `dronewatch-bench --config deploy/config.yaml`
прогонить найгірший потоп (випадкові детекції від усіх датчиків, утричі більше за стелю) і скаже, чи вкладається скан у `scan_dt`
(код виходу 1, якщо ні). `dronewatch-bench --sweep` друкує таблицю «скан залежно від стель».

Тести: `pytest` із кореня (фейковий годинник, секунди замість хвилин). Алгоритм fusion лежить у `src/dronewatch/fusion`.

## AI-асистент оператора (RAG + tool-calling)

Чат у дашборді: оператор питає природною мовою («що зараз у Зоні A?», «чи був такий інцидент раніше?»), а
агент на Mistral AI сам вирішує, які реальні дані подивитись — через чотири read-тули (`get_state`, `get_sensors`,
`get_incidents`, `search_similar_incidents`) над тим самим `Engine`, що й HTTP API. `search_similar_incidents` —
семантичний пошук схожих минулих тривог у Qdrant (ембединги `mistral-embed`), а не keyword-grep: кожна нова тривога
індексується туди в момент появи.

**Повністю необов'язковий шар.** `ai.enabled: true` без `MISTRAL_API_KEY` у середовищі не заважає сервісу
стартувати й трекати дрони — AI-асистент просто вимкнений, `/api/ai/ask` відповідає 503 з поясненням. Так само
недоступність самого Qdrant чи Mistral під час роботи (мережа, ключ скінчився) ніколи не рахується помилкою скану
і не впливає на `/api/state`, `/ws` чи журнал тривог: AI-шар живе в окремих фонових задачах, не в циклі сканування.

**Загрози.** Агент має лише read-тули — нічого не пише в систему (не підтверджує тривог, не змінює конфіг, не
керує датчиками). Дані з тулів (стан датчиків, текст інцидентів) завжди йдуть у запит до LLM окремим
`role: tool` повідомленням і в системному промпті прямо названі даними для читання, а не інструкціями — агент не
виконує команди, які могли б опинитися всередині такого тексту. `POST /api/ai/ask` захищений так само, як інші
read-ендпоінти (вхід обов'язковий), і має м'який ліміт запитів на користувача (десять за хвилину) — публічний
показ не повинен перетворюватись на необмежені платні виклики до Mistral.

**Увімкнути в Docker:**

    MISTRAL_API_KEY=ваш_ключ docker compose --profile demo-sensors --profile ai up --build

Це піднімає додатково сервіс `qdrant` (профіль `ai`, лише у внутрішній мережі, без зовнішнього порту). Без
`MISTRAL_API_KEY` чи без профілю `ai` стенд піднімається так само, просто без AI-панелі в дашборді.

**Перед показом:** Qdrant порожній одразу після піднятого стенду, тож перше запитання про «схожий випадок»
законно отримає «нічого не знайдено». Дайте емулятору прогнати кілька сценаріїв до того, як підходити до людей —
тоді в індексі вже буде що шукати.

Поза контейнером: `pip install -e ".[dev]"` ставить `httpx` і `qdrant-client` разом з рештою залежностей;
конфіг — розділ `ai:` у `config.example.yaml`.
